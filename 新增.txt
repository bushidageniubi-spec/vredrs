C* 语言完整技术文档（语言名字叫C+*）

版本 1.0 | 基于 Vredrs 前端 | 面向裸机与高性能计算

---

一、设计哲学

1.1 定位

C*（读作 "C Star"）是 Vredrs 生态中专门面向裸机（Bare Metal）、高性能计算和系统底层控制的编译目标层。它不是一门独立语言，而是 Vredrs 的 “物理引擎扩展”。

1.2 核心原则

· 前端完全复用 Vredrs：词法、语法、AST 与 Vredrs 完全一致。开发者不需要学习新语法，只需改变文件后缀名。
· 后端完全独立：不继承 Vredrs 的 ARC/GC/协程运行时，而是使用极简的线性类型 + 区域分配 + 内联汇编后端。
· 极简代码量：C* 后端的核心代码控制在 5000 行以内（不含 AI 生成的模板）。
· 编译期物理编排：将“硬件特性（DMA、Cache、中断、Flash）”作为编译参数，而非运行时配置。

1.3 文件约定

· 源文件后缀：.cpps（C Star Source）
· 输出产物：.o（对象文件）、.a（静态库）、.bin（裸机固件）
· 编译命令：vredrs build --raw 自动识别 .cpps 文件并调用 C* 后端

---

二、C* 新增语法（仅 5 个扩展）

以下语法在 Vredrs 解析器中会被识别并保留，但只有 C* 后端会对其做特殊处理。

2.1 指针类型 ptr[T]

```cpps
set, reg_base = 0x40020000 as ptr[u32]
set, val = reg_base.load()           # 原子读取
reg_base.store(0x1234)               # 原子写入
```

语义：定义指向内存地址的指针。支持 load()、store()、load_acquire()、store_release() 等原子操作。

---

2.2 易变修饰 volatile

```cpps
volatile set, status_flag = 0x00     # 禁止编译器优化掉对该变量的读写
```

语义：告诉编译器该变量可能被硬件（中断/DMA）修改，每次访问都必须从内存重新读取。

---

2.3 对齐修饰 align(N)

```cpps
align(64) struct, DMA_Descriptor
    u32 src
    u32 dst
    u32 len
    u32 ctrl
/end
```

语义：强制结构体按 N 字节对齐，用于 DMA 描述符、Cache Line 对齐的缓冲区。

---

2.4 内联汇编 asm { ... }

```cpps
unsafe
    asm {
        "mov eax, 1"
        "int 0x80"
    }
/end
```

语义：直接嵌入目标架构的汇编代码。支持输入/输出操作数约束（类似 GCC 内联汇编）。

---

2.5 段修饰 @section("name")

```cpps
@section(".text.boot")
fn, _start()
    # 引导代码
/end
```

语义：将函数或变量放置在指定的链接段中，用于控制内存布局（如启动代码、中断向量表）。

---

三、极端功能详解

3.1 编译时 DMA 流水线编排（@pipeline）

痛点：手写 DMA 驱动需要精确控制数据搬运与 CPU 计算的交错时序。

C* 方案：

```cpps
@pipeline(priority="cpu_bound")
fn, process_data(src: ptr[u8], dst: ptr[u8], len: u32)
    for i in 0..len
        dst[i] = src[i] * 2
    /end
/end
```

编译器行为：

· 自动将循环切割为“计算窗口”与“DMA 搬运窗口”。
· 根据 CPU 主频与 RAM 突发传输长度，动态调整流水线深度。
· 生成 CPU 与 DMA 指令交错的机器码，实现零开销并行。

---

3.2 固件差分原子更新（@patch）

痛点：OTA 升级需要生成差分包，通常依赖外部工具，流程割裂。

C* 方案：

```cpps
@patch(base="firmware_v1.bin", output="update.patch")
fn, build_new_firmware()
    set, new_version = "1.1"
/end
```

编译器行为：

· 内部维护“符号到物理地址”的映射表。
· 检测变量变化后，直接对比新旧映射表，计算字节级差分。
· 在编译期间时生成差分包，无需外部工具。

---

3.3 确定性中断聚类（@isr_group）

痛点：中断优先级分配依赖经验，高优先级中断可能饿死低优先级。

C* 方案：

```cpps
@isr_group(budget_us=50, priority="high")
fn, uart_isr()
    # 处理 UART 数据
/end

@isr_group(budget_us=200, priority="low")
fn, timer_isr()
    # 处理定时器
/end
```

编译器行为：

· 静态分析每个中断函数的汇编指令数，计算最坏情况执行时间（WCET）。
· 如果实际耗时超过声明预算，编译报错。
· 自动排列中断向量表，计算最优抢占优先级和子优先级。

---

3.4 混合内存缓存预取（@prefetch）

痛点：Cache Miss 延迟是 CPU 计算的 50~100 倍，普通编译器无法跨函数预取。

C* 方案：

```cpps
@prefetch(hint="sequential", stride=64)
fn, process_array(arr: ptr[u32], len: u32)
    for i in 0..len
        process(arr[i])
    /end
/end
```

编译器行为：

· 将循环拆为“预取窗口”和“计算窗口”。
· 根据 RAM 突发传输长度自动调整步长。
· 生成 __builtin_prefetch 指令，将 Cache Miss 率压至理论最低。

---

四、包管理系统：按物理尺寸自动分区

4.1 设计目标

在裸机环境中，不同大小的文件应存储在不同物理介质（Flash/SRAM/EEPROM）中，以优化访问速度与磨损均衡。

4.2 使用方式

在 .cpps 文件中定义仓库配置：

```cpps
@repo {
    url: "https://github.com/verse-pkg/",
    split_by: "size",
    thresholds: [4096, 65536, 1048576],
    output: "flash_layout.h"
}

# 之后只需导入包名
import, "tiny_crypto"      # 自动分配到 <4KB 目录
import, "fat_fs"           # 自动分配到 >64KB 目录
```

4.3 编译器行为

· 拉取所有依赖包，计算编译后二进制体积。
· 按阈值自动创建子目录（如 small/、medium/、large/）。
· 生成物理偏移映射表，嵌入固件头部。
· Bootloader 根据包大小快速计算加载地址，零查找开销。

4.4 附加功能

· 按哈希去重：相同二进制的包自动硬链接合并。
· 热/冷分区：高频访问包分配到 SRAM，冷启动包分配到 Flash。
· 字节级回滚：新包体积变化时，自动重新计算后续偏移，原子写入 MBR。

五、融入现有 Vredrs 架构

5.1 双轨编译模型

```
源代码
├── main.vr          → Vredrs 标准前端 → AST → Vredrs 后端（ARC/GC/LLVM）
├── driver.cpps      → Vredrs 标准前端 → AST → C* 后端（线性类型/裸机）
└── assets.cpps      → Vredrs 标准前端 → AST → C* 后端（包管理/资产生成）
```

· .vr 文件走“诗意轨道”，处理逻辑与并发。
· .cpps 文件走“物理轨道”，处理内存与硬件。

5.2 编译流程

```bash
vredrs build --raw main.vr
```

内部执行：

1. 扫描项目文件，按后缀分组。
2. .vr 文件 → Vredrs 编译器（语义检查 + LLVM 通用后端）。
3. .cpps 文件 → C* 编译器（线性类型检查 + 极简 LLVM/汇编后端）。
4. 链接器合并所有 .o 文件，输出 .elf 或 .bin。

5.3 互操作机制

· 跨文件调用：.vr 中可声明 extern fn, dma_copy(src, dst, len)，实现在 .cpps 中。
· 共享类型：Vredrs 的 struct 可在 C* 中用作 ptr[T] 的基类型。
· 链接时合并：两个后端的 LLVM IR 在链接层统一，确保最终二进制无冲突。

C* 包管理系统完整技术文档

版本 1.0 | 面向裸机固件的物理感知包管理

---

一、设计哲学

1.1 核心问题

在裸机开发中，包管理不仅仅是"下载依赖"，更关键的是：

· 存储介质分区：不同大小的文件应放在 Flash/SRAM/EEPROM 的不同区域。
· 固件体积控制：每个字节都珍贵，必须精确管理。
· OTA 更新效率：差分包需要知道每个包的物理偏移。

1.2 设计目标

· 零运行时开销：包索引在编译期生成，固件运行时直接使用静态偏移表。
· 物理感知：根据包的二进制大小自动分配到最优存储区域。
· 原子化操作：整个包目录是一个原子单元，任何变化触发全量偏移重新计算。
· 对开发者透明：只需在 .cpps 中声明 @repo 配置，其余由编译器自动处理。

---

二、核心机制

2.1 包的定义

每个 C* 包是一个独立的 .cpps 文件或目录，包含：

· 源代码（.cpps 文件）
· 元数据（package.cpps 或内联注解）
· 编译后的二进制产物（由 C* 后端生成）

包的声明方式：

```cpps
@package {
    name: "tiny_crypto",
    version: "1.2.0",
    author: "verse-embedded",
    license: "MIT",
    description: "轻量级 AES-128 实现，适用于 Cortex-M0+",
    threshold_hint: "small"        # 可选，建议编译器将其归类为小包
}
```

关键元数据：

· threshold_hint：开发者可建议分类（small/medium/large），但编译器拥有最终决定权（基于实际编译体积）。

---

2.2 仓库配置

在项目的根目录或任意 .cpps 文件中定义仓库：

```cpps
@repo {
    # 包源
    sources: [
        "https://github.com/verse-pkg/",
        "https://gitlab.com/verse-embedded/",
        "local: ./vendor/"
    ],
    
    # 物理分区策略
    split_by: "size",               # 按编译后体积分类
    thresholds: {
        sram: [0, 4096],            # 0-4KB → SRAM（高速）
        flash_fast: [4096, 32768],  # 4-32KB → Flash 快速区域
        flash_normal: [32768, 524288], # 32-512KB → Flash 普通区域
        flash_archive: [524288, 0]  # >512KB → Flash 归档区域
    },
    
    # 输出配置
    output: {
        header: "flash_layout.h",   # 生成的偏移映射表（C\* 兼容头文件）
        map: "layout.map",          # 人类可读的布局报告
        binary: "pkg_index.bin"     # 固件中嵌入的二进制索引
    }
}
```

---

2.3 依赖声明

在 .cpps 文件中声明依赖：

```cpps
# 按名称导入，编译器自动归类
import, "tiny_crypto"
import, "fat_fs"
import, "lwip"

# 导入并强制指定分区（覆盖编译器自动分类）
import, "critical_boot" to sram
import, "big_assets" to flash_archive
```

---

三、编译器行为（详细流程）

阶段 1：扫描与下载

1. 扫描项目中所有 import 声明。
2. 从 @repo 配置的 sources 中拉取包。
3. 下载到本地缓存（~/.cpps/cache/）。

阶段 2：编译与大小计算

1. 对每个包独立调用 C* 后端编译，生成临时 .o 文件。
2. 计算 .o 文件的最终二进制体积（去除调试信息、符号表后）。
3. 记录体积到元数据表。

阶段 3：物理分类

1. 按 thresholds 配置，将包分配到对应的物理分区。
2. 生成分区目录结构：
   ```
   build/
   ├── sram/
   │   ├── tiny_crypto.o
   │   └── critical_boot.o
   ├── flash_fast/
   │   ├── lwip.o
   │   └── driver_uart.o
   ├── flash_normal/
   │   └── middleware.o
   └── flash_archive/
       └── big_assets.o
   ```

阶段 4：偏移表生成

1. 按分区顺序计算每个包的加载地址（load_addr）。
2. 生成静态结构体数组：

```cpps
// 自动生成的 flash_layout.h
struct PkgEntry {
    const char* name;
    u32 load_addr;
    u32 size;
    u8 checksum[32];
};

const PkgEntry PKG_INDEX[] = {
    {"tiny_crypto",   0x20000000, 2048,  {0x1A, 0x2B, ...}},
    {"critical_boot", 0x20000800, 1024,  {0x3C, 0x4D, ...}},
    {"lwip",          0x08002000, 32768, {0x5E, 0x6F, ...}},
    // ...
};
```

阶段 5：去重与硬链接合并

1. 计算每个包的 SHA-256 哈希。
2. 如果两个包生成完全相同的 .o（例如标准库的 memcpy 实现），在文件系统层面创建硬链接，物理存储只保留一份。
3. 更新偏移表，指向同一块物理地址。

阶段 6：原子写入

1. 将所有分区产物合并为一个单一的固件镜像。
2. 将 PKG_INDEX 嵌入固件头部。
3. 生成主引导记录（MBR），包含偏移表的起始地址和 CRC32 校验。

---

四、运行时行为

4.1 Bootloader 加载流程

1. 上电后，Bootloader 读取固件头部的 PKG_INDEX 地址。
2. 验证 CRC32。
3. 遍历 PKG_INDEX，根据 load_addr 直接将每个包加载到对应内存地址。
4. 跳转到 main()。

全程零动态内存分配，零哈希查找，直接指针解引用。

4.2 包访问 API（在 Vredrs 中调用）

```vredrs
import, "cpps/runtime"

set, crypto = cpps.load_pkg("tiny_crypto")
if crypto != null
    # 调用包中的函数（通过 C\* 生成的符号表）
    crypto.aes_encrypt(data)
/end
```

五、高级功能

5.1 热/冷分区策略

在 @repo 中标记热路径包：

```cpps
@repo {
    hot_threshold: 10,          # 被访问超过 10 次的包 → SRAM
    cold_threshold: 1,          # 只被访问 1 次的包 → Flash Archive
}
```

编译器会统计编译期已知的调用关系（静态分析），自动调整分区。

5.2 差分更新（与 @patch 联动）

当包版本更新时：

1. C* 后端对比新旧版本的包偏移表。
2. 计算字节级差分，生成 .patch 文件。
3. OTA 更新时，Bootloader 只下载差异部分，用 memcmp 定位变化点，原子写入。

5.3 版本回滚（原子级）

· 每次更新前，将旧版本偏移表写入备份区域。
· 若新固件启动失败，Bootloader 自动从备份区域恢复旧偏移表，回滚到字节级精准状态。

七、与 Vredrs 生态的集成点

7.1 跨语言符号导出

· C* 包可以用 @export 导出函数供 Vredrs 调用。
· Vredrs 中可用 extern fn, ... 声明并在链接时绑定。

7.2 统一的版本管理

· vpm（Vredrs 包管理器）与 C* 的 @repo 共享同一个版本锁定文件（verse.lock）。
· 两者在同一个构建系统中自动协调依赖版本。

八、总结

C* 包管理系统不是"包管理器"，而是 "固件物理布局引擎"。它的核心价值在于：

1. 编译期决策：所有分区、去重、偏移计算在编译期完成，运行时零开销。
2. 物理感知：根据包大小自动分配合适的存储介质，这是硬件工程师才会关心的细节，被纳入了编译器流程。
3. 原子化更新：整个包目录是一个原子单元，版本回滚精确到字节。
4. 开发者透明：从声明依赖到生成固件，开发者只需写几行配置，编译器搞定其余一切。

它让裸机开发者从"手动管理 Flash 分区"的痛苦中彻底解放出来，把时间还给真正的逻辑设计。
C* 的核心理念是 “极简抽象，暴力发射”。它不与 Vredrs 通用后端共享任何优化管道，彻底分道扬镳。

如果我来设计 C* 的后端架构，我会把它拆成 “四层漏斗”，从上到下逐步剥离 Vredrs 的高级语义，最终变成纯粹的机器指令。核心目标是：用 5000 行核心 Rust 代码，驱动 AI 生成的数万行模板代码。

---

各层核心实现细节

Layer 1: 语义过滤器（~800 行 Rust）

这是 C* 后端的“安检门”。它遍历 Vredrs AST，执行两道关卡：

· 拒绝关：如果遇到 spawn、async、await、try、catch 节点，直接编译报错，提示“这些特性仅限 .vr 文件使用”。
· 注入关：自动为每个 ptr[T] 类型插入线性状态标记。例如：
  ```rust
  // 开发者写：
  set, buf = 0x20000000 as ptr[u8]
  
  // 语义过滤器内部标记为：
  // 类型: ptr[u8], 线性状态: Unconsumed
  // 必须在作用域结束前调用 .free() 或传递给另一个线性函数
  ```

Layer 2: 物理中间表示 (PIR)（~1500 行 Rust）

这是 C* 最核心的创新。PIR 不是传统的 SSA (静态单赋值) 形式，而是一种 “带物理坐标的 DAG (有向无环图)”。

PIR 节点示例：

```rust
enum PIRNode {
    // 内存操作（带对齐信息）
    Store { addr: u32, value: PIRNode, align: u8 },
    // 原子操作（带内存顺序）
    AtomicCAS { addr: u32, expected: PIRNode, desired: PIRNode, order: Ordering },
    // DMA 请求（带突发长度）
    DMARequest { src: u32, dst: u32, len: u32, burst: u8 },
    // 中断注册（带优先级）
    ISR { handler: fn_ptr, priority: u8, budget_cycles: u64 },
}
```

关键转换：循环展开与预取插入
遇到 for 循环时，PIR 生成器会：

1. 根据 CPU 的 Cache Line (64字节)，自动计算步长。
2. 在循环体内插入 prefetch 节点（提前 3 次迭代加载数据）。
3. 检查相邻迭代间是否无依赖，若是，自动生成 DMARequest 节点卸载数据搬运。

Layer 3: 资源布局引擎（~2000 行 Rust）

这是 C* 的“房地产开发商”——负责给每个变量、函数、包分配物理地址。

· 包分区算法：读取 @repo 配置中的 thresholds，对每个包调用 Size Estimator（基于 LLVM 的 Module 大小估算），然后贪心分配到 sram、flash_fast、flash_normal 桶中。
· 中断优先级排序：读取 @isr_group 中的 budget_us，使用单调速率调度（Rate-Monotonic Scheduling）算法，自动计算出最优抢占优先级，输出到中断向量表。
· DMA 流水线调度：将 PIR 中的 DMARequest 和 CPU 计算节点视为有向依赖图。使用列表调度（List Scheduling） 算法，在满足依赖关系的前提下，尽量将 DMA 请求提前，覆盖 CPU 计算延迟。

接口函数：

```rust
fn assign_partitions(packages: &[Package]) -> PartitionMap;
fn schedule_isrs(isrs: &[ISRNode]) -> VectorTable;
fn pipeline_dma(graph: &mut DAG) -> Schedule;
```

Layer 4: 代码发射器（~700 行 Rust + AI 生成的模板）

架构策略：核心逻辑只负责遍历 PIR 节点并调用生成函数，具体的指令生成交给数千行 AI 生成的模板代码。

· LLVM 后端（主）：
  · 将 PIR 节点映射到 LLVM IR 指令：Store → store i32，AtomicCAS → cmpxchg。
  · 用 LLVM 的寄存器分配器解决 ARM/RISC-V 的寄存器压力问题（省去手写寄存器分配算法）。
· 直接汇编后端（备）：
  · 遇到 asm { ... } 块，直接复制字符串。
  · 对于简单指针操作，直接生成 .word 和 .byte 伪指令。
· 包元数据输出：生成一个只读的 .rodata 段，包含 { name: *const u8, addr: u32, size: u32, checksum: [u8; 32] } 数组，供 Bootloader 读取。

---

与 Vredrs 标准后端的融合机制（链接层）

最终的 .o 文件由两个独立后端生成：

· Vredrs 后端：生成 main.vr.o（包含协程调度器、GC、spawn 逻辑）。
· C* 后端：生成 driver.cpps.o（包含 _start 引导、中断向量表、DMA 控制函数）。

链接器脚本规则：

```
SECTIONS {
    .text.boot   : { *(.text.boot) }   > FLASH  (C* 的 _start 必须放在最前面)
    .text        : { *(.text) }        > FLASH  (Vredrs 的业务逻辑)
    .rodata      : { *(.rodata) }      > FLASH
    .data        : { *(.data) }        > SRAM
    .bss         : { *(.bss) }         > SRAM
}
```

运行时启动流程：

1. CPU 上电 → 跳转到 _start（来自 .cpps）。
2. C* 初始化栈指针、清零 .bss、设置中断向量表。
3. C* 调用 main()——而 main() 函数体实际在 .vr 文件中定义。
4. Vredrs 运行时在 main() 中初始化协程调度器，开始执行业务逻辑。
5. 当中断触发时，C* 的中断服务函数直接调用 Vredrs 导出的 extern fn on_interrupt()。

为何这套架构能压在 5000 行核心代码？

关键：把“脏活”抽象成“数据表”和“AI 模板”

· 指令映射表：不是写 match 分支处理每个 ARM 指令，而是维护一个 JSON 映射表（AI 生成）：{"PIR::Store": "str %v, [%addr]"}
· 调度算法：列表调度、单调速率调度都是经典算法，核心实现各约 100 行。
· 链接器脚本：固定模板，通过 @section 注解动态填充。

唯一需要手写维护的是 PIR 结构定义和语义过滤器——这是 C* 的灵魂，AI 写不了。其余全部可 AI 化。

如何确保前端完全复用？

1. 词法/语法解析：C* 文件使用同样的 Lexer 和 Parser，只是新增的语法（ptr[T]、asm、注解等）已经在 AST 中作为特殊节点保留，现有前端不会报错（因为 Expr 和 Stmt 枚举已包含 Unsafe、Asm 等变体，且注解可以忽略）。
2. 语义分析：C* 需要自己的语义过滤，但可以复用 semantic/resolver.rs 构建符号表，然后在此基础上覆盖检查规则。
3. 中间表示：C* 不使用 ir 目录下的通用 IR，而是新建 PIR，所以完全不依赖现有的 ir/builder.rs。

结论：你在 codegen/cstar/ 下写你的后端，前端（lexer/parser/semantic）的代码一行都不用改，只需在 mod.rs 和 main.rs 中增加几行路由判断即可。这样既保持了“双轨制”的独立，又实现了“同一前端”的复用。

清晰分工：什么属于 Vredrs，什么属于 C*

Vredrs 的聚焦（.vr 文件）

· 业务逻辑（if/else、for、match）。
· 高级并发（spawn、channel、async/await）。
· 动态数据结构（list、dict、tuple）。
· 外部调用接口（通过 extern 调用 C* 生成的符号）。
· 字符串处理、JSON、HTTP、文件 I/O（依赖操作系统）。

C* 的聚焦（.cpps 文件）

· 操作系统内核入口（_start 引导、中断向量表）。
· 硬件寄存器操作（ptr[T] + volatile）。
· 中断服务函数（@isr_group）。
· DMA 流水线编排（@pipeline）。
· 固件包管理（@repo + import 按大小分区）。
· 任何需要精确时钟周期或内存地址的底层代码。

交互方式：Vredrs 如何调用 C*

在 .vr 文件中声明一个外部符号，具体实现在 .cpps 中：

```vredrs
// main.vr
extern fn, dma_copy(src: ptr[u8], dst: ptr[u8], len: u32)

fn, main()
    set, src_buf = [1,2,3,4,5]   # Vredrs 管理的数据
    # 调用 C* 实现的 DMA 搬运
    dma_copy(src_buf.as_ptr(), 0x20000000, 5)
/end
```

编译时，Vredrs 编译器会链接 C* 生成的 .o 文件中的 dma_copy 符号，最终合成一个完整的二进制。

对于你现有的 codegen/ 目录的变化

你无需删除任何 Vredrs 后端代码，只需调整路由逻辑：

```rust
// src/codegen/mod.rs
pub fn compile_file(path: &str, backend: BackendKind) -> Result<()> {
    let ext = Path::new(path).extension().unwrap_or_default();
    match ext.to_str() {
        Some("vr") => {
            // Vredrs 标准编译路径（不含裸机特性）
            compile_vredrs(path, backend)
        }
        Some("cpps") => {
            // 强制使用 C* 后端，忽略 backend 参数
            compile_cstar(path)
        }
        _ => Err("Unsupported file extension".into())
    }
}
```

这样用户只需要切换文件后缀名（.vr ↔ .cpps），编译器会自动选择对应的后端。Vredrs 的前端 Parser 完全不变，只是当遇到 asm 或 ptr[T] 节点时，Vredrs 后端会报错，而 C* 后端会正常处理。
